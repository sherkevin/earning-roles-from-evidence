\begin{abstract}
Large Language Model (LLM) multi-agent systems are usually built around either centralized orchestrators or preassigned specialist roles. Both assumptions are convenient, but they hide a more fundamental scientific question: how can useful division of labor emerge when agents have only local visibility, no global expert catalog, and no predeclared identities? We \emph{propose} \textbf{Emergent Delegation Organization (EDO)}, a decentralized framework in which near-homogeneous agents interact over sparse connected graphs and repeatedly choose among three primitive actions: solve the task themselves, outsource it to a visible neighbor, or split it into subtasks. Each delegation creates an upstream acceptance obligation, and these obligations compose into a recursive acceptance ladder; social reputation is therefore shaped not by self-report but by whether downstream work is accepted and ultimately contributes value to the global task. The proposed framework yields a structured personality-tag space that drives future local allocation decisions. We further position our current executable system, based on \textbf{Terminal-Consensus Peer Backpropagation (TCPB)}, as a restricted Stage-1 instantiation of this broader framework: fixed topologies, role-prior nodes, linear handoff packets, and terminal outcome calibration only. We honestly report that on a single benchmark (HotpotQA, $n{=}200$, single seed), the TCPB instance is Pareto-dominated by a simpler self-claim baseline at equal token cost, and we treat this as a delivered-system limitation rather than a refutation of the broader framework. The main contribution is therefore the EDO framework and its Stage-2 mechanism designs (recursive split, recursive audit, vector-belief routing) as proposed components, together with an honest Stage-1 measurement that motivates the full theory's empirical evaluation in future work; the Stage-2 mechanisms are theoretical in this submission, while the delivered TCPB prototype implements only terminal-outcome calibration.
\end{abstract}

\section{Introduction}

The dominant design patterns in LLM-based multi-agent systems make a strong assumption before the system has even started to work: either a central orchestrator decides who should do what \citep{wu2023autogen,hong2024metagpt,shen2023hugginggpt}, or each agent is assigned a fixed specialist identity in advance \citep{qian2024chatdev,chen2024agentverse}. These strategies can be effective engineering shortcuts, but they leave open a more basic question about organization. In realistic collaborative settings, useful division of labor is rarely known perfectly at initialization time. Groups begin with partial knowledge, repeated interaction, local judgments, and uneven structural exposure. Over time, some members become recognized as better decomposers, others as reliable integrators, others as useful auditors or bridge-builders. In other words, organization is not only executed; it is formed.

This paper takes that organizational view seriously. We ask whether a society of near-homogeneous language agents, each with only local neighbor visibility on a sparse connected graph, can self-organize into useful task division through recursive delegation, recursive acceptance, and value-based social updating. Our interest is therefore not simply in improving multi-agent answer quality by adding more dialogue turns or building a stronger router. We study how tasks move through a constrained society, how local trust is formed, when agents decide to keep work, when they outsource it, when they split it, and how these repeated interactions induce recognizable organizational structure.

The failure mode motivating our work remains \textbf{delegation miscalibration}. Prior systems often assume that an agent can accurately assess whether it should accept a task or hand it off. In practice, LLMs are prone to overconfident self-assessment \citep{guo2017calibration,kadavath2022know}: they often accept work they should not keep, delay delegation, or pass forward low-quality intermediate results. Earlier versions of our project showed that replacing self-reflection \citep{shinn2023reflexion,madaan2023selfrefine} with terminal outcome feedback significantly improves delegation safety on fixed-topology benchmarks. However, we now argue that this is only the first layer of a richer theory. Delegation quality is not just a routing score problem; it is a problem of organizational emergence under local interaction.

We therefore propose \textbf{Emergent Delegation Organization (EDO)} as the full long-paper method. In EDO, agents start from the same cognitive machinery and the same action grammar. The only allowed asymmetries arise from graph position, local interaction history, and the task neighborhoods each agent encounters over time. Every task is treated as a node in a task tree, not merely as a single linear message. Upon receiving a task, an agent chooses among three primitive actions: \texttt{do\_self}, \texttt{outsource(neighbor)}, or \texttt{split(subtasks)}. Importantly, each outsourcing decision also creates a recursive accountability chain: if agent $a$ delegates to $b$, then $a$ is responsible for accepting, revising, rerouting, or rejecting $b$'s returned result. This recursive audit structure turns delivered value, not self-description, into the basis of social reputation.

Under this framing, an agent's ``personality'' is not a stylistic prompt trait but a structured operational tag vector induced by interaction history (acceptance rate, decomposition usefulness, integration quality, rework cost, solving efficiency). Future local delegation decisions compare task demands against these socially formed tags under local visibility constraints, asking the more ambitious question of whether useful division of labor can emerge from local interaction alone. We explicitly separate theory from currently executed evidence: our present codebase implements a restricted Stage-1 system, \textbf{Terminal-Consensus Peer Backpropagation (TCPB)} --- fixed \texttt{chain} and \texttt{star} topologies, role-prior nodes, linear handoff packets, and terminal-only competence updates on the final accepting node --- which already provides a reproducible, fully logged baseline showing that decentralized outcome-based calibration reduces premature acceptance and stabilizes routing without centralized orchestration. We reinterpret that system as the first executable approximation of the broader organizational framework, not as the final method.

Our contributions are therefore four-fold:
\begin{enumerate}
  \item We reframe decentralized multi-agent routing as a problem of \textbf{organizational emergence under local interaction}, rather than merely better static role assignment or router tuning.
  \item We introduce \textbf{Emergent Delegation Organization (EDO)}, a method built around sparse local graphs, recursive \texttt{do / outsource / split} decisions, recursive upstream acceptance audits, and value-induced personality tags.
  \item We formalize the distinction between the \textbf{full long-paper method} and the \textbf{current restricted executable instantiation}, positioning TCPB as a Stage-1 prototype rather than the endpoint of the research line.
  \item Using current HotpotQA evidence, we show that even the restricted instantiation already supports the central direction: decentralized outcome-based calibration improves delegation safety and creates measurable route stabilization without relying on a central controller.
\end{enumerate}

\section{Related Work}

\subsection{Routing and orchestration in multi-agent systems}

Much of the LLM multi-agent literature is organized around central decomposition and routing. \textbf{AutoGen} \citep{wu2023autogen} provides a generic conversation framework where a manager agent dispatches sub-tasks to specialist agents; \textbf{MetaGPT} \citep{hong2024metagpt} hard-codes a software-engineering pipeline (PM $\to$ architect $\to$ engineer) where each agent's role and order are pre-assigned; \textbf{HuggingGPT} \citep{shen2023hugginggpt} uses an LLM controller to plan, select, and execute models from a global tool catalog. These orchestrator-based frameworks achieve strong control and interpretability, but they share three properties our work specifically removes: (i) a globally visible expert/role table at initialization, (ii) a central decision node that owns all routing, and (iii) a fixed task script. \textbf{ChatDev} \citep{qian2024chatdev} and \textbf{AgentVerse} \citep{chen2024agentverse} extend the orchestrator paradigm with richer agent communication and emergent behaviors but still rely on either a manager agent or globally synchronized state. Our work asks the complementary question: how can division of labor emerge when no node has a global expert table and each node sees only its local sparse-graph neighborhood?

\subsection{Reflection, critique, and outcome-based calibration}

Reflection has become a common mechanism for improving LLM reasoning. \textbf{Reflexion} \citep{shinn2023reflexion} introduces verbal RL where an agent critiques its own trajectory and rewrites a policy. \textbf{Tree-of-Thoughts} \citep{yao2023tot} backtracks across self-evaluated reasoning branches. \textbf{Self-Refine} \citep{madaan2023selfrefine} iteratively rewrites outputs based on the model's own feedback. At the multi-agent level, \textbf{Multi-Agent Debate} \citep{liang2023mad,du2024improving} and \textbf{ChatEval} \citep{chan2024chateval} replace self-critique with explicit per-hop peer critique that a meta-reviewer aggregates. All these approaches assume that agents (or the aggregating reviewer) are at least moderately reliable judges of competence within a single turn. Our prior work found that self-reflection is especially unreliable when the question is not ``is this sentence better?'' but ``should I have handled this task at all?''\,---\,a delegation, rather than generation, decision. This motivates our emphasis on terminal, outcome-grounded feedback rather than per-hop peer scoring: in the restricted TCPB prototype, only terminal outcomes are used for calibration. In the full EDO framework, terminal outcomes are retained but augmented by recursive upstream acceptance signals that are local, structured, and audit-like rather than free-form opinion exchanges.

\subsection{Division of labor, reputation, and local organization}

Our long-paper framing is closer to a theory of organization than to static role play. Classical organization theory \citep{galbraith1973designing,mintzberg1979structuring} establishes that stable roles in human groups are outcomes of repeated coordination, evaluation, and structural position rather than perfect advance assignment, and that reputation is socially constructed through accepted contributions rather than self-claims. Local neighborhood structure also matters: sparse connectivity creates bridge positions, clustered exposure, and bounded trust propagation. EDO imports these intuitions into language-agent systems by making local delegation, recursive acceptance, and value-based personality formation the primary objects of study.

\subsection{Problem formulation}

We model a multi-agent society as a sparse connected directed graph $\mathcal{G} = (\mathcal{A}, \mathcal{E})$, where $\mathcal{A} = \{a_1, a_2, \dots, a_N\}$ is the set of agents and $\mathcal{E}$ defines allowed communication channels. The full EDO framework targets near-homogeneous initialisation where agents share base cognitive machinery and action grammar, with only mild asymmetry from graph position and interaction history. The delivered Stage-1 TCPB prototype operates in a more restricted regime --- \emph{decentralized within a fixed role-prior topology with hand-tuned safety priors} (role-prior nodes \texttt{decomposer}/\texttt{evidence\_seeker}/\texttt{verifier}/\texttt{synthesizer} and a hand-coded force-forward gate, with routing weights locally computed); near-homogeneous initialisation with role-priors removed is reserved for Stage-2 (\S\ref{sec:experiments} E1).

Each input instance $x = (q, y, C)$ consists of a question $q$, gold answer $y$, and optional supporting context $C$. In the full method, $x$ expands into a \textbf{task tree} rather than a single linear message. Each task node records its parent, children, current uncertainty, required output, evidence state, owner agent, executor agent, candidate result, and audit status. This representation is necessary because a task may be solved directly, outsourced intact, or recursively split into subtasks that later require integration and audit.

\subsection{Agent state and personality}

At time $t$, each agent $a_i$ maintains state
\[
S_i^t = \{P_i^t, B_i^t, M_i^t, H_i^t, \mathcal{N}(i)\},
\]
where $P_i^t$ is the agent's public personality-tag vector, $B_i^t$ is its local belief state over neighbors, $M_i^t$ is its private episodic memory, $H_i^t$ is a summary of past delegation and audit interactions, and $\mathcal{N}(i)$ is its visible neighbor set.

The key object is $P_i^t$, the \textbf{value-induced operational persona}. This is not a stylistic role prompt. It is a structured vector whose components summarize socially observed capability, for example:
\begin{multline*}
P_i = [\text{solve}, \text{decompose}, \text{audit}, \text{integrate},\\
\text{explore}, \text{efficiency}, \text{reliability}].
\end{multline*}
These components are intended to capture how useful the agent has been to others in the society: whether its outputs are accepted, whether it reduces or increases rework, whether its decompositions help, whether its integrated outputs are reliable, and whether it achieves useful work efficiently.

Each agent also maintains only \textbf{local} beliefs about neighbors. There is no global competence directory. For a neighbor $a_j$, the local belief $B_i^t(j)$ is constructed from interaction history with $a_j$, recent publicly visible persona summaries, and local audit outcomes involving $a_j$. This preserves decentralization while allowing trust and specialization to be gradually formed.

\subsection{Task signatures and local utility}

Instead of matching tasks to fixed role names, EDO represents each task node $z$ by a task-signature vector
\begin{multline*}
\phi(z) = [\text{need\_decompose}, \text{need\_verification},\\
\text{need\_integration}, \text{need\_exploration},\\
\text{evidence\_breadth}, \text{uncertainty}, \text{cost\_sensitivity}].
\end{multline*}
This task signature can be extracted through rules, light-weight LLM judgment, or future learned modules. The key point is conceptual: routing should be based on the match between task demands and socially formed personality tags, not on a hard-coded role lookup and not necessarily on a large embedding router.

We define the demand--persona matching function as the normalised inner product $\mathrm{Fit}(P, \phi){=}\langle P,\phi \rangle / (\lVert P\rVert\cdot\lVert\phi\rVert)\in[0,1]$; in Stage-1 TCPB, $P$ and $\phi$ collapse onto a scalar (mean-axis fold) so $\mathrm{Fit}$ degenerates to a one-dimensional comparison.

For an agent $a_i$ receiving task node $z$, the three candidate utilities are:
\begin{align*}
U_i^{\mathit{self}}(z) ={} & \mathrm{Fit}(P_i, \phi(z)) \\
                           & - \lambda_c \mathrm{Cost}_{\mathit{self}}(z) \\
                           & - \lambda_r \mathrm{Risk}_{\mathit{self}}(z), \\
U_i^{\mathit{out}}(z, j) ={} & \mathrm{Fit}(B_i(j), \phi(z)) \\
                            & - \lambda_s \mathrm{SendCost}(i,j) \\
                            & - \lambda_a \mathrm{AuditCost}(z) \\
                            & - \lambda_r \mathrm{RejectRisk}(j,z), \\
U_i^{\mathit{split}}(z) ={} & \mathrm{SplitGain}(z) - \lambda_m \mathrm{MergeCost}(z) \\
                            & - \lambda_d \mathrm{DepthPenalty}(z) \\
                            & - \lambda_a \mathrm{AuditLoad}(z).
\end{align*}
The selected action is
\begin{align*}
\pi_i(z) = \arg\max \big\{ & U_i^{\mathit{self}}(z), \;\; U_i^{\mathit{split}}(z), \\
                            & \textstyle\max_{j \in \mathcal{N}(i)} U_i^{\mathit{out}}(z,j) \big\},
\end{align*}
subject to budget, depth, and safety constraints.

\subsection{Recursive upstream audit}

The main departure from the current prototype is that delegation is not terminal at handoff time. Every outsourcing decision also creates an \textbf{acceptance obligation}. If $a$ delegates a task to $b$, then $a$ must later evaluate whether to accept $b$'s result, reject it and redo the task, reject it and reroute, or reject it and resplit.

This produces a recursive structure. If $a \rightarrow b \rightarrow c$, then $b$ audits $c$ before returning upward, and $a$ audits $b$. The system therefore operates on a \textbf{delegation tree with a recursive acceptance ladder}, not merely on a one-dimensional chain of messages. This is essential because social reputation should be grounded in accepted delivered value, not only in terminal answer correctness.

\subsection{Personality-tag update}

Each audit event generates a local social signal for the downstream executor. For a parent-upstream node $u$, downstream node $v$, and task node $z$, a local audit event can be written as:
\begin{multline*}
\ell_{u \rightarrow v, z} = [\text{accepted}, \text{rework\_cost},\\
\text{value\_gain}, \text{timeliness},\\
\text{decomposition\_help}, \text{integration\_help}].
\end{multline*}
After the root task finishes, the system also observes a terminal event
\begin{multline*}
r_{\mathrm{terminal}}(x) = [\text{quality}, \text{total\_cost},\\
\text{total\_depth}, \text{final\_accept}].
\end{multline*}
The full update rule combines local accepted-value signals with slower terminal correction:
\begin{align*}
P_i^{t+1} = \mathrm{clip}\Big(&(1-\mu) P_i^t + \mu \big(\eta_{\mathrm{loc}} \mathrm{LocalValue}_i^t \\
&+ \eta_{\mathrm{trm}} \mathrm{TerminalValue}_i^t \\
&- \eta_{\mathrm{rew}} \mathrm{ReworkPenalty}_i^t \big)\Big).
\end{align*}

\subsection{Current restricted executable instantiation: TCPB prototype}

The full EDO Stage-2 execution loop is a recursive \textsc{Process} function that selects among the three primitive actions (R1 \textsc{DoSelf} / \textsc{Outsource} / \textsc{Split}), performs per-handoff audit (R2) on every \textsc{Outsource} return, and updates the vector belief $B_i^{t+1}(j)$ via an EMA step (R3) for each audit event in the resulting task tree. The complete pseudocode, including the recursion bounds ($H_{\max}{=}4$, $d_{\max}{=}3$, $n_{\max}{=}12$, $k_{\max}{=}3$), the four-class \textsc{Audit} decision protocol, and the Stage-1 fallback projection, is given in Algorithm~\ref{alg:edo-stage2-loop} (Appendix~E). The reported empirical results in Table~\ref{tab:main-results} come from the degenerate Stage-1 instance of this loop, which we call \textbf{Terminal-Consensus Peer Backpropagation (TCPB)}: \textsc{Split} is disabled, \textsc{Audit} defaults to \textsc{Accept} on every return, and the vector belief $B_i^t(j)$ is collapsed onto a scalar $c[i]$ via mean-axis fold. With these collapses, the Stage-1 TCPB outsourcing utility reduces to the explicit weighted form
\[
U^{\text{out}}_i(z, j) \;=\; 0.55\,c[j] + 0.20\,\mathrm{accept}(j) + 0.10\,\mathrm{forward\_bias}(j) - \lambda_a\,\mathrm{audit}(z),
\]
where $c[j]\in[0,1]$ is the scalar competence projection of $B_i(j)$, $\mathrm{accept}(j)$ is $j$'s historical acceptance rate as upstream auditor, $\mathrm{forward\_bias}(j)$ is a topology-driven flow prior, and $\lambda_a{=}0.02$ is the accept margin. The Prototype Scope Box below restates this restriction component-by-component.

\subsection{Why the separation matters}

Without separating the full EDO method from the current TCPB prototype, the paper falls into one of two traps. If we write only what the code already does, the paper becomes a fixed-role routing paper with limited conceptual novelty. If we write only the grand theory and ignore implementation limits, reviewers will rightly reject the paper for overclaiming. The correct scientific stance is to make EDO the main theory and TCPB the current restricted instantiation. The exact boundary between the two is fixed by the Prototype Scope Box that follows.

\section{Experiments}
\label{sec:experiments}

\subsection{What current evidence already establishes}

Our current reproducible evidence comes from the Stage-1 TCPB prototype on HotpotQA. The main benchmark slice is a fixed set of 200 HotpotQA validation questions, frozen as a versioned slice in the anonymous code/data supplement. Existing runs compare \texttt{fixed\_peer\_calibrated}, \texttt{fixed\_self\_calibrated}, \texttt{fixed\_self\_claim}, \texttt{fixed\_static\_roles}, and centralized baselines under shared inputs and logged execution traces.

These experiments do \emph{not} establish the full EDO theory. What they do establish is narrower but still important:
\begin{itemize}
  \item decentralized outcome-based calibration matters;
  \item delegation safety is measurable and improvable;
  \item structured intermediate state is necessary for route-level auditing;
  \item route preferences can stabilize without a central controller;
  \item some remaining errors are generated by local answer bottlenecks rather than by routing failure.
\end{itemize}
This evidence should be presented as support for the \textbf{direction} of the theory, not as proof of the entire organizational framework.

\subsection{Stage-1 setup: current prototype experiments}

Metrics consolidated in the per-run \texttt{main\_table.csv}.

\paragraph{Finding 1: Backbone quality dominates all method differences.} All three Stage-1 methods improve by $+15$ to $+20$ F1 points when switching from \texttt{glm-4-flash} to \texttt{gpt-4.1-mini} on the same 200-sample slice and identical routing code. The routing mechanism is secondary to generation quality on this benchmark/topology combination.

\paragraph{Finding 2: Method ordering is backbone-sensitive and must not be over-interpreted from a single backbone.} On \texttt{glm-4-flash} (Stage-1 GLM), the ordering was \texttt{static\_roles} $>$ \texttt{peer\_calibrated} $\approx$ \texttt{self\_claim}. On \texttt{gpt-4.1-mini}, the ordering inverts: \texttt{self\_claim} (F1=0.7641) $>$ \texttt{static\_roles} (0.7454) $>$ \texttt{peer\_calibrated} (0.7381). Figure~\ref{fig:backbone-sensitivity} visualises the inversion under identical inputs and routing code.

The three-method ordering above is therefore supported by chain-200 evidence ($n{=}200$) only and should not be presented as a finalized full-validation ranking.

\paragraph{Finding 3: PAR collapses to zero regardless of backbone.} All three methods achieve PAR$={=}0.0$ on \texttt{gpt-4.1-mini}, consistent with the GLM result. The PAR$=0$ outcome is attributable to the decomposer force-forward gate (Algorithm~\ref{alg:edo-stage2-loop} line 11), a fixed safety prior that already saturates PAR for \texttt{self\_claim} and \texttt{static\_roles}; the TCPB peer-calibration mechanism itself does not provide additional PAR reduction in the delivered Stage-1 configuration. The safety \emph{gate} is robust to backbone change; TCPB's PAR contribution on top of the gate is not demonstrated here.

\paragraph{Finding 4: On a capable backbone, TCPB peer-calibration overhead does not yield F1 gains.} The F1 and cost data indicate that \texttt{peer\_calibrated} uses the same token budget as \texttt{self\_claim} (both 6{,}414/sample) but achieves lower F1. The mechanism value of TCPB on this configuration appears in route-level process metrics (MHC$=2.00$ for peer, indicating fuller chain use) rather than in final F1. For a capable backbone on HotpotQA, the simpler methods are Pareto-dominant on the F1/cost frontier. The paper contribution should therefore pivot from ``\texttt{peer\_calibrated} is best'' to ``the EDO framework explains when and why delegation overhead pays off --- and Stage-1 evidence reveals backbone-sensitive threshold effects that motivate the full theory.''

\subsection{Full EDO experimental agenda (Stage-2 plan)}

The full long-paper requires experiments redesigned around emergence, organised around five studies: \textbf{E1} emergent specialisation (persona-tag divergence, specialisation entropy, per-agent action frequencies); \textbf{E2} recursive \texttt{split} value (usefulness, merge overhead, depth, rework delta); \textbf{E3} recursive audit value (precision/recall, low-quality propagation, post-rework quality); \textbf{E4} sparse-graph robustness (chain, star, random, small-world, community-bridge); \textbf{E5} benchmark transfer to MuSiQue and other compositional tasks. None of these organisational metrics is claimed by the present submission.

\subsection{Current Stage-1 artifact interpretation}

Stage-1 ablations (Table~\ref{tab:ablations}) show that on the weak backbone the answer-generation bottleneck dominates the routing-mechanism contribution, $\pm 2\times$ weight-sensitivity sweeps yield $<0.003$ pp F1 change, and \texttt{peer\_calibrated} reproduces ${\sim}52\%$ of static routes. These narrow Stage-2 targets to task trees, recursive audit, persona tags, and sparse-graph organisation. A preliminary 3-shard $\times$ 200-sample paired run of a degenerate-Stage-2 prototype (\texttt{edo\_stage2\_chain}) on HotpotQA, included for completeness in Appendix~D, suggests the action-policy menu can compress token cost without harming F1, but the F1 effect is inside noise at this sample size; we therefore do not include it in the main results until the deferred multi-seed bootstrap (\S Limitations item~(4)) lands.

\section{Conclusion}

We \emph{proposed} \textbf{Emergent Delegation Organization (EDO)}, a framework that studies multi-agent language systems as \textbf{organizations} rather than as collections of prompts, and asks how labor division, local trust, and durable social identity emerge from repeated delegation, acceptance, and value-based updating. EDO \emph{proposes} three moves --- from fixed roles toward socially induced personality tags, from linear routing toward recursive task trees, and from terminal-only supervision toward recursive acceptance-based organization. None is empirically demonstrated here; the delivered \textbf{TCPB} system is a restricted Stage-1 instantiation that implements only the third (terminal supervision) in fixed-topology, role-prior form, and is Pareto-dominated by a simpler self-claim baseline at equal token cost on a single benchmark --- a delivered-system limitation, not a refutation of the broader framework. The HotpotQA evidence supports only the narrower premise that decentralized outcome-based calibration improves delegation safety (PAR$=0$, attributable to the safety gate) without centralized control. The long-paper opportunity lies in implementing and empirically evaluating the Stage-2 mechanisms (R1 split, R2 audit, R3 vector-belief routing).

\section*{Limitations}
\label{sec:limitations}

We explicitly acknowledge seven scope limitations of the present submission. (1) The current runtime implements only the restricted Stage-1 TCPB prototype: fixed topologies, role-prior nodes, linear packet passing, deterministic accept-or-forward routing, and terminal-only outcome updates. It therefore cannot yet establish the strongest claims of the full EDO framework --- recursive split value, local audit superiority, or personality-tag emergence from near-homogeneous initialization. (2) Some current routing improvements remain partially entangled with hand-designed safety priors and answer-generation constraints; the present evidence should be interpreted as validating the Stage-1 premise that decentralized outcome-based calibration helps, not as a full proof that local interaction alone suffices for rich organizational emergence across arbitrary settings. (3) Backbone-sensitive method ordering: on our 200-sample HotpotQA chain slice, the relative ranking of Stage-1 delegation methods inverts between the weak and strong backbone (Table~\ref{tab:main-results}, Finding~2). The TCPB peer-calibration overhead does not yield F1 gains when the underlying model is already strong enough to self-evaluate accurately. We \emph{conjecture} that the full EDO organizational advantage will be most visible on harder tasks, weaker individual agents, or richer topologies where single-agent self-assessment breaks down; this conjecture is not validated by the present submission and will be tested by the Stage-2 evaluation agenda (\S 4.4 E1--E5). (4) Statistical evidence is presently limited to point estimates with $n{=}200$: paired-bootstrap confidence intervals, multi-seed variance, and explicit significance tests are deferred to the Stage-2 evaluation agenda (\S 4.4 E1--E5). (5) \textbf{Cross-endpoint comparability is an open variable}: a provider-side data-integrity event during this submission cycle led to a deliberate switch of the upstream OpenAI-compatible API channel serving the strong backbone, with the two affected method runs queued for re-execution under the new endpoint while the unaffected full-validation result in Table~\ref{tab:main-results} is preserved as-is. The engineering response (fail-fast integrity guard, endpoint switch, re-execution plan) is documented in Appendix~B; from a scope-of-claims perspective, this means cross-endpoint comparability between the original Table~\ref{tab:main-results} numbers and the deferred re-runs is presently an open variable rather than a settled measurement. (6) \textbf{Delivered-system Pareto-domination}: the delivered TCPB Stage-1 instance is Pareto-dominated by \texttt{fixed\_self\_claim} on F1 at equal token cost on the chain-200 HotpotQA slice with \texttt{gpt-4.1-mini} (Finding~4); we report this as a delivered-system limitation rather than as evidence against the broader EDO framework, since the dominance is established only on a single benchmark $\times$ single seed $\times$ single backbone configuration, and the EDO Stage-2 mechanisms (R1 split, R2 audit, R3 vector-belief routing) that are hypothesised to reverse this ordering on harder compositional tasks are not implemented in the present submission. (7) \textbf{Demographic and societal scope}: the only benchmark used (HotpotQA) is sourced exclusively from English Wikipedia and skews toward Western, biographical, and factual entities; the present evaluation does not test multilingual generalisation, low-resource language behaviour, or culturally diverse query distributions. Whether the EDO organisational claims, the TCPB Stage-1 calibration mechanism, or the proposed Stage-2 R1/R2/R3 mechanisms hold in non-English or domain-shifted settings is an open question; no broader societal-impact study is conducted in this submission.

These limitations are not accidental flaws in reporting. They define the boundary between the current restricted instantiation and the long-paper method it motivates. The next-stage implementation burden is therefore clear: introduce task-tree state, recursive audit, persona-tag updates, and general sparse-graph support, then test whether the stronger organizational predictions of EDO hold empirically.

\section*{Appendix B: Provider Integrity Event --- Engineering Response}
\label{sec:appendix-b}

This appendix documents the engineering response to the provider-side data-integrity event referenced in \S Limitations item~(5). It is placed in the appendix per the EMNLP/ACL convention that Limitations should describe the scope and consequence of issues, while the corresponding engineering implementation belongs in supplementary material.

\paragraph{Event description.} During the full-validation pass on the strong backbone, two of the three method runs were silently affected by an upstream provider issue in which the requested model identifier was routed to a different (newer) underlying model for a subset of API calls; the third method's full-validation result was not affected.

\paragraph{Runtime guard.} The runtime client was extended with a fail-fast integrity check that compares the model identifier echoed back in each API response against the requested identifier and raises an explicit error on mismatch. The check operates per-call, before any downstream consumption of the response content.

\paragraph{Endpoint switch.} The upstream API endpoint serving the strong backbone was switched to a different OpenAI-compatible provider channel with the integrity guard enabled in pre-send mode: a known-fake model identifier raises immediately without issuing a request, demonstrating the guard's pre-flight effectiveness.

\paragraph{Affected results disposition.} The two affected method runs are queued for re-execution under the new guard and the new endpoint. The third (unaffected) full-validation result reported in Table~\ref{tab:main-results} is preserved as-is, since invalidating it would discard reproducible evidence without obtaining new information. Cross-endpoint comparability between the original Table~\ref{tab:main-results} numbers and the deferred re-runs is the corresponding scope-of-claims caveat recorded in \S Limitations item~(5).

\section*{Appendix C: LLM Prompt Templates}
\label{sec:appendix-c}

For reproducibility (per Reviewer R-FULL-004 D5 request), this appendix lists the four LLM-call templates referenced by Algorithm~\ref{alg:edo-stage2-loop}: \textsc{LLM\_Answer} (line 13), \textsc{LLM\_Decompose} (line 26), \textsc{Audit} (line 7, optional LLM-fallback variant), and \textsc{Evidence\_Extract} (line 33). All four are released verbatim in the anonymous code/data supplement; abridged versions are reproduced below.

\paragraph{C.1 \textsc{LLM\_Answer} (per-agent answer/forward template).}
A shared prefix establishes the global contract (local visibility only, plain-text output, HotpotQA short-answer style); per-role suffixes refine output for \texttt{decomposer}, \texttt{evidence\_seeker}, \texttt{verifier}, and \texttt{synthesizer} nodes. The synthesizer follows a two-stage internal protocol: (i) a brief "Key facts" recap reading all evidence lines from first to last, then (ii) deriving a single shortest answer span. The forward branch (when an agent forwards rather than answers) outputs exactly one short sentence adding one new fact or subgoal-relevant clue.

\paragraph{C.2 \textsc{LLM\_Decompose} (R1 \texttt{split} template).}
Takes one complex question and outputs at most $k_{\max}{=}3$ atomic, independently-answerable subquestions in strict JSON. Hard requirements: each subquestion is solvable in isolation (no inter-subquestion chain); each yields a concrete fact (no meta-questions); the original question is never reproduced as a subquestion; if no atomic decomposition is possible, the template returns \texttt{\{"subtasks": []\}} and the runtime downgrades to \textsc{DoSelf}. Each subquestion carries a \texttt{task\_type\_guess} hint $\in$ \{\texttt{factoid}, \texttt{comparison}, \texttt{aggregation}, \texttt{verification}\} for downstream routing. Two worked decomposition examples (a comparison and an aggregation) are included in the prompt body.

\paragraph{C.3 \textsc{Audit} (R2 audit decision template, LLM-fallback variant).}
The default audit is rule-based (no LLM call) per the Algorithm~\ref{alg:edo-stage2-loop} default. The optional LLM-fallback variant takes an upstream--downstream pair $(u, v)$, a task node $z$, and a candidate result $r$, and outputs a strict JSON object \texttt{\{decision, value\_gain, rework\_cost, rationale\}} with \texttt{decision} $\in$ \{\textsc{Accept}, \textsc{AcceptWithNote}, \textsc{RejectReroute}, \textsc{RejectResplit}\}. Decision rules (verbatim from the prompt): \textsc{Accept} when the candidate plausibly answers the subtask; \textsc{AcceptWithNote} when usable but incomplete or low-confidence; \textsc{RejectReroute} when wrong/empty AND another neighbour has a reasonable chance; \textsc{RejectResplit} when wrong AND the failure looks structural. \texttt{value\_gain}$\in[0,1]$ measures movement toward the root task; \texttt{rework\_cost}$\in[0,1]$ defaults to $1{-}\texttt{value\_gain}$.

\paragraph{C.4 \textsc{Evidence\_Extract} (R3 vector-belief update mapping).}
This is a deterministic rule-based mapping (no LLM call), not a prompt template. Given an audit event $e$ and the task signature $\phi(z)$, it projects $e$ onto the $7$-dimensional persona axes $[\text{solve}, \text{decompose}, \text{audit}, \text{integrate}, \text{explore}, \text{efficiency}, \text{reliability}]$ via a lookup-table from $e.\text{decision}$ and $e.\text{value\_gain}$ to per-axis EMA increments, weighted by $\phi(z)$'s axis prominence. The full mapping table appears in the anonymous executable specification supplement \S 4.

\section*{Appendix E: EDO Stage-2 Execution Loop (Pseudocode)}
\label{sec:appendix-e}

This appendix gives the full pseudocode for the EDO Stage-2 execution loop referenced from \S 3.6, \S 3.9, and Finding~3 in \S 4.3. Section 3.6 of the main body specifies the prose semantics and the Stage-1 TCPB scoring formula; this appendix records the operational form. Empirical numbers in Section~\ref{sec:experiments} come from the degenerate Stage-1 instance only --- \textsc{Split} is disabled, \textsc{Audit} defaults to \textsc{Accept}, and the vector belief is collapsed via mean-axis fold (Prototype Scope Box, item (v)). Deterministic instantiations of $\phi$, $\textsc{Fit}$, and $\textsc{evidence\_extract}$ are given in the executable spec [Anonymous Suppl.] \S 1--3.

\begin{algorithm}[!ht]
\caption{EDO Stage-2 execution loop (single sample, recursive). The full EDO mechanism integrating R1 \texttt{split}, R2 recursive audit, and R3 vector-belief routing. Table~\ref{tab:main-results} reports the degenerate Stage-1 instance (TCPB) where \textsc{Split} is disabled and \textsc{Audit} defaults to \textsc{Accept}.}
\label{alg:edo-stage2-loop}
\small
\begin{algorithmic}[1]
\Require Root task $z_0$, gold $y$; agent set $\mathcal{A}$ with sparse adjacency $\mathcal{N}$; vector belief $B_i^{t}{:}\,\mathcal{A}{\times}\mathcal{A}{\to}[0,1]^{7}$ (R3); empty task tree $\mathcal{T}$ rooted at $z_0$; constants $H_{\max}{=}4$, $F_{\textsc{th}}{=}0.5$, $\delta_a{=}0.02$, $\nu{=}0.2$, $k_{\max}{=}3$, $d_{\max}{=}3$, $n_{\max}{=}12$.
\Ensure Predicted $\hat{y}$; updated belief $B^{t+1}$.
\Function{Process}{$z, i, \mathcal{T}$}
  \State $\phi \gets \textsc{extract}(z)$ \Comment{rule, no LLM call}
  \State $U^{\textsc{s}} \gets \textsc{Fit}(P_i,\phi) - \lambda_c\textit{Cost}_{\textit{self}}$
  \For{$j \in \mathcal{N}(i)$}
    \State $U^{\textsc{o}}_j \gets \textsc{Fit}(B_i^{t}(j),\phi) - \lambda_a\textit{AuditCost}$
  \EndFor
  \State $U^{\textsc{p}} \gets \textsc{SplitGain}(z) - \lambda_m\textit{MergeCost}$ \Comment{R1}
  \If{$\textit{depth}(z){\geq}d_{\max}$ \textbf{or} $|\mathcal{T}|{\geq}n_{\max}$}
    \State $U^{\textsc{p}} \gets {-}\infty$ \Comment{bound: SPLIT disabled}
  \EndIf
  \State $a \gets \arg\max\{U^{\textsc{s}},\,\max_j U^{\textsc{o}}_j,\,U^{\textsc{p}}\}$
  \If{$a{=}\textsc{DoSelf}$}
    \State \Return $\textsc{LLM\_answer}(z,P_i),\,\textsc{Accept}$
  \ElsIf{$a{=}\textsc{Outsource}(j^{\star})$}
    \State $r,\textit{stat} \gets \textsc{Process}(z, j^{\star}, \mathcal{T})$
    \State $e \gets \textsc{audit}(i,j^{\star},z,r)$ \Comment{R2; rule-based; no LLM call by default}
    \State $\mathcal{T}.\textsc{apply\_audit}(z,e)$ \Comment{writes \texttt{audit\_status}; jsonl-buffered}
    \If{$e.\textit{decision}{\in}\{\textsc{Accept},\textsc{AcceptWithNote}\}$} \Return $r, e.\textit{decision}$ \EndIf
    \If{$e.\textit{decision}{=}\textsc{RejectReroute}$ \textbf{and} unvisited $j' \in \mathcal{N}(i)$ exists}
      \State \Return \textsc{Process}$(z, j', \mathcal{T})$
    \Else \, $a \gets \textsc{Split}$ \Comment{escalate to RESPLIT}
    \EndIf
  \EndIf
  \If{$a{=}\textsc{Split}$}
    \State $\{z_1,\!\dots\!,z_k\} \gets \textsc{LLM\_decompose}(z)$ with $k{\leq}k_{\max}$ \Comment{R1}
    \State $\mathcal{T}.\textsc{add\_children}(z,\{z_l\})$
    \State \Return $\textsc{integrate}(\{\textsc{Process}(z_l,i,\mathcal{T})\}_{l=1}^k),\,\textsc{Accept}$
  \EndIf
\EndFunction
\State $\hat{y},\_ \gets \textsc{Process}(z_0, \textit{root\_agent}, \mathcal{T})$
\Statex \quad\textit{// R3 vector-belief update (one EMA step per audit event)}
\For{$e \in \mathcal{T}.\textit{audit\_events}$}
  \State $B_i^{t{+}1}(j) \gets \textsc{clip}\!\big((1{-}\nu) B_i^{t}(j) + \nu\cdot \textsc{evidence\_extract}(e,\phi(z)),0.05,0.95\big)$
\EndFor
\Statex \quad\textit{// Stage-1 fallback: terminal scalar update on root accepting agent (TCPB)}
\State $r \gets {+}1$ \textbf{if} $F_1(\hat{y},y){\geq}F_{\textsc{th}}$ \textbf{else} ${-}1$;\, project $B^{t{+}1} \to c$ via mean-axis fold (cf.\ Prototype Scope Box (v))
\State \Return $\hat{y},\,B^{t+1}$
\end{algorithmic}
\end{algorithm}
