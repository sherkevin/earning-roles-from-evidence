# AAMAS 评审规则：从真实合作者判断中形成职责

版本：2026-09-24  
用途：用 AAMAS 审稿人的标准，判断本项目的故事是否已经成为一篇可信、可复现、值得接收的论文。  
适用对象：以“agent 通过真实协作者对交付物的判断、使用和返工，获得后续职责”为中心的 agent/协作论文。  
本规则不是审稿结果，也不是方法设计；它规定什么证据出现后，才允许把故事写成论文结论。

## 1. 审稿人首先要听懂的故事

论文必须能用一段话说清楚：

> 初始没有固定专家身份的 agent，在真实有依赖的协作中交付工作；实际 owner 或 consumer 对交付作行动前判断，并在后续使用、修改、拒绝或返工中留下可审计证据；这些判断经过明确的角色更新规则，改变被评价 agent 在未来任务中的职责；agent 的经验、记忆和 workflow 也随协作历史共同变化。论文检验这种角色证据是否比同信息的简单信任或匹配规则更能改善后续任务质量与完整成本。

这条故事有六个必须相连的箭头：

```text
真实依赖工作
  → 具体交付物
  → 真实接收者的行动前判断
  → 实际采用 / 修改 / 拒绝 / 返工
  → 被评价者的角色证据
  → 未见任务中的未来职责与团队效用
```

如果论文只展示其中一个箭头，必须把结论收窄到那个箭头。不能用“有消息、有反馈、有角色标签”替代完整链条。

## 2. AAMAS 审稿人会重点检查什么

### 2.1 问题是否真实且重要

合格论文要说明：

- 为什么固定角色或中央 pooled controller 在这个协作场景中不够；
- 为什么实际接收者的判断比一个事后总分、统一 verifier 或自我描述多提供了信息；
- 为什么判断会影响未来职责，而不是只影响当前答案；
- 为什么这个过程必须允许 agent 和 workflow 共同变化；
- 质量收益与额外模型调用、审查、通信、返工成本之间的关系是什么。

审稿人会警惕以下说法：

- “agent 会自然形成角色”，但实验预先固定了 producer、reviewer 和 lead；
- “没有中央调度器”，但所有职责和候选人都由实验脚本指定；
- “workflow 共演”，但 workflow 从头到尾没有改变；
- “贡献更公平”，但没有定义公平对应的可观测量；
- “接受率提高”，但没有证明未来任务中发生了有益的职责变化。

### 2.2 方法是否只有一个可识别的核心机制

论文必须明确只把一个主要机制当作贡献：

```text
输入：谁在什么任务语境下，如何评价谁的哪份交付
更新：评价如何进入被评价者的角色证据
决策：角色证据如何影响下一个合法职责机会
反馈：后来什么证据可以修正早先判断
```

其余内容应作为共同环境规则、实现基础或单独消融。不能同时把以下东西都写成新方法：

- 能力学习；
- 贡献归因；
- 信誉传播；
- 角色绑定；
- workflow 搜索；
- 子任务分解；
- 交接修复；
- 记忆检索。

如果把这些模块同时打开，审稿人无法判断最终收益来自哪里。

必须区分两个状态：

- `P_v(c)`：关于被评价 agent `v` 在职责情境 `c` 中的、可以按权限传播的角色证据；
- `B_u(v,c)`：某个 owner `u` 对 `v` 的私有、局部信任。

如果未来仍由同一个直接评价候选者的 owner 选择候选者，结果可能只是 `B_u` 学得更好，不能声称学到了可传播的 `P_v`。

### 2.3 角色更新是否可执行、可审计、可反驳

审稿人应能从论文复现一次完整更新，不依赖作者口头解释。至少需要：

- 事件格式：producer、recipient、任务/依赖情境、交付哈希、逐项来源、判断时间、计划使用、实际使用、修改、返工、成本、workflow 版本；
- 合法观察边界：模型在线时能看到什么，哪些 scorer、gold、盲审标签只能离线使用；
- `UNKNOWN` 规则：超时、来源不足、使用归因不明、接收者自身错误不能被偷偷变成失败；
- 判断者校准：如何估计 judge 的误报、漏报或情境偏差；
- 更新函数：输入、参数、先验、遗忘/漂移、传播权限和一次事件是否只能更新一次；
- 未来职责决策：候选集合、探索概率、平局、成本和权限如何处理；
- 纠错机制：后来终局结果怎样修正局部判断，但不能把团队总失败简单归责给上游 producer。

一个只有“接受则加一、拒绝则减一”的公式，除非证明它在信息、成本或因果识别上超出同信息 bandit，否则只能作为 baseline。

### 2.4 因果识别是否成立

接收者说“好”不等于交付有因果价值。审稿人会问：

1. 接收者如果没有看到交付，是否仍能独立完成同样任务？
2. 交付是否减少了核查、返工或失败概率？
3. 接收者的行动是否真的使用了 producer 的主张，而不是碰巧做出了相同动作？
4. producer 的来源是否覆盖了实际使用的每条关键主张？
5. 后续失败来自 producer 内容、来源不足、consumer 自己的错误，还是环境/预算？
6. 交付可见性、任务难度、接收者能力和调用预算是否同时变化？

最小的边际价值量应明确相对于一个可执行替代方案，例如 recipient-alone、另一 producer 或同状态的 fallback：

```text
ΔQ = 后续官方任务质量(看到交付) − 后续官方任务质量(替代方案)
ΔC = 完整系统成本(看到交付) − 完整系统成本(替代方案)
```

如果使用配对世界、随机隐藏交付或固定状态重放，必须报告生产、接收、审查、通信、重放和失败的全部成本。稀疏反事实校正本身已有近邻方法，不能直接作为创新声明。

### 2.5 未来职责是否真的改变

角色学习的最低证据不是 posterior 变化，而是**后续真实责任机会发生变化**。论文要展示：

- 未来任务在任何执行或评分前，owner 的候选集合、所见证据和选择概率已封存；
- 被选 agent 实际执行了新职责；
- 该选择使用的是合法传播的角色证据，而不是研究者事后指定；
- 至少有一个此前没有直接评价候选者的 owner，能够根据同一公开记录做选择；
- 选择结果在未见任务上改变了质量、成本或返工；
- 角色证据与同信息 raw acceptance、contextual trust/bandit、terminal-only 和 pooled controller 的差异被测量。

没有第三方 owner 时，结论应收窄为“某个局部 owner 的信任更新”，不能写成角色形成或角色传播。

### 2.6 agent–workflow 共演是否是真实变量

论文不需要把 workflow 共演包装成第二个算法，但必须记录它是否发生。审稿人会查看：

- 初始 workflow、任务机会、权限、通信图和非目标更新规则是否相同；
- 各组是否允许根据真实经历形成不同的记忆、依赖、交接和返工结构；
- `W_t → W_{t+1}` 的变化是否有日志；
- role evidence 改变的是职责，还是仅仅改变了 prompt 中的一个标签；
- 是否把候选方法已经形成的记忆和 workflow 复制给 live control，造成信息泄漏；
- 如果 workflow 实际被冻结，论文是否诚实地把结论缩成固定任务图中的职责选择。

短期 clone/swap/replay 只能解释局部机制，不能代替长期 full-policy stream 的共演证据。

### 2.7 相关工作和创新边界是否诚实

审稿人会要求论文正面比较以下近邻，而不是只在 related work 中列名字：

- task-specific trust 与 contextual bandit；
- Meta-Team 的下游反馈、teammate profile 和组织角色更新；
- RAPS 的直接评价、第三方 witness、witness credibility 和动态订阅；
- Sero/RepuNet 的贡献信誉与角色/网络变化；
- C3 的固定历史反事实 credit；
- DecisionBench 的旧轨迹能力卡与后续委派；
- DAC 的下游 consumer 判断作为上游训练信号；
- Marginal-Contribution Policy Gradients 的 learned contribution 加稀疏反事实校正。

以下内容不能单独构成创新：

- “其他 agent 评价 agent”；
- “评价结果改变角色”；
- “稀疏图中的信誉传播”；
- “用接受率更新能力”；
- “少量 replay 校准评价”；
- “workflow 与 agent 一起演化”；
- “把 agent 从 generic pool 分成 specialist”。

可接受的创新必须是一个可执行、可识别、经过强基线比较的更窄机制，或者一个可靠的负结果，例如证明真实 consumer-use 信号在某些观察约束下不能比普通 trust 更好。

## 3. 必须通过的证据门

下面六道门是 P0。任何一道没有通过，都不能以完整的“role formation”故事投稿。

| 门 | 审稿问题 | 通过证据 |
|---|---|---|
| P0-1 问题 | 是否存在真实的 producer–consumer 依赖？ | consumer 必须能接受、使用、修改、拒绝或返工具体交付；不能只是两个被脚本命名的单 agent 片段 |
| P0-2 机制 | 是否有唯一的 judgment→role update？ | 完整伪代码、合法信息边界、`UNKNOWN`、校准、传播和未来选择规则 |
| P0-3 识别 | judgment 是否与实际边际价值有可检验关系？ | 预冻结的 visible/hidden、fallback、replay 或其他可识别设计，含完整成本 |
| P0-4 角色 | 角色证据是否改变未来职责？ | 未直接评价候选者的 owner 在未见任务中依据封存记录选择并执行候选者 |
| P0-5 对照 | 是否击败或解释同信息强基线？ | raw acceptance、terminal-only、contextual trust/bandit、close method、pooled controller，均等信息和预算 |
| P0-6 纵向结果 | 是否改善长期团队目标？ | 多个独立 task/root stream 上报告官方质量、完整成本、失败类型、置信区间和选择概率 |

### P0 门的严格失败条件

以下任一情况出现，审稿决定至少是 Reject/Strong Reject，除非论文主动收窄主张：

- consumer 没有真实行动或使用记录；
- producer、consumer、reviewer、lead 等席位由脚本预设，且论文称其为涌现角色；
- 后续职责从未改变，或改变只来自研究者手工绑定；
- 交付内容、接受判断和终局成功被混成一个标签；
- 使用了在线不可见的 gold、私有 scorer 或未来评分来更新角色；
- 只有一个任务、一个 agent family 或一次成功轨迹；
- 后续 owner 就是直接评价候选者，无法区分公共角色证据和私有信任；
- 普通同信息 bandit/controller 可以逐步复现所有更新和选择，但论文没有承认；
- 只报告成功率，不报告审查、通信、重试、模型调用和反事实成本；
- 只挑成功交付、成功判断或有利任务，删失和 UNKNOWN 没有分母；
- 结果依赖泄漏的任务类型、benchmark 名称、gold-derived feature 或候选方法的后记忆复制；
- 论文声称 workflow 共演，但没有 workflow 状态轨迹或冻结/演化消融。

## 4. 好论文与坏论文的可观察差别

| 好论文 | 坏论文 |
|---|---|
| 用一个清晰问题：判断何时能成为未来职责证据 | 同时宣称能力学习、贡献分配、信誉、workflow 搜索和角色涌现 |
| 交付、判断、使用、返工、后续职责各有独立记录 | 用一个“accepted=1/failed=0”标签解释一切 |
| 明确区分 `P_v` 与 `B_u(v)` | 直接评价候选者的 owner 继续选人，却称为公共角色形成 |
| 预冻结未来选择，评分在选择后进行 | 看完结果后决定给谁什么职责 |
| 使用真实依赖任务和自然交接 | 给单 agent 代码片段贴 producer/consumer 名字 |
| 对照读取同样事件并支付同样成本 | 只和 fixed role 或弱 self-report 比较 |
| 报告负例、删失、失败归因和完整成本 | 删除 timeout、失败交付和未完成链条 |
| 结论范围与实验范围一致 | 一个 AppWorld 单例推广到一般多 agent 组织 |
| 能说清楚什么结果会推翻自己的方法 | 任何正结果都被解释成 role learning |

## 5. 审稿评分规则

总分 100；但不是简单平均。P0 门是前置条件。

| 维度 | 权重 | 10 分标准 |
|---|---:|---|
| 问题与意义 | 15 | 真实协作痛点清楚，未来职责有实际后果，问题范围可控 |
| 核心机制 | 20 | 一个精确定义、可运行、可审计、可反驳的 judgment→role update |
| 因果与实验 | 25 | 能区分判断相关性、交付边际价值、选择效应和终局归因 |
| 创新与定位 | 15 | 超出近邻或给出有价值的受控负结果，且有忠实强基线 |
| 长期共演证据 | 15 | 多个独立流中 agent/workflow 变化、未来职责和团队效用相互连接 |
| 复现与表达 | 10 | 原始日志、版本、成本、失败、任务划分和信息边界完整，故事紧凑 |

建议解释：

- 85–100：Strong Accept 候选；所有 P0 通过，贡献边界很清楚；
- 75–84：Accept/Weak Accept 候选；可能有局部实验或写作缺口，但主闭环已成立；
- 60–74：Major Revision；故事有价值，但缺一项重要因果或长期证据；
- 0–59：Reject；核心对象、方法或证据无法识别。

即使总分很高，只要 P0-2、P0-3 或 P0-4 未通过，也不能给 Accept。一个漂亮的终局成功率不能补齐缺失的判断到角色闭环。

## 6. 审稿人必须问的十个问题

1. 交付如果没有被展示，接收者会做什么？这个替代路径真实可执行吗？
2. 接收者实际使用了 producer 的哪一条主张？来源在哪里？
3. 接收者的错误、producer 的错误和环境失败分别如何记账？
4. 哪个状态代表“被评价 agent 的角色证据”？谁能读、谁能改、谁能传播？
5. 未来职责改变发生在什么时候？选择在评分前还是评分后封存？
6. 未来 owner 是否直接评价过候选者？如果是，如何排除私有 trust 解释？
7. 同信息 contextual bandit 或 pooled controller 能否模拟每一步？
8. 角色变化是否在独立 task/root 上产生质量或成本收益？
9. 所有 judgment、audit、communication、retry、replay 和 token 是否计入成本？
10. 哪一种预先声明的结果会让作者停止声称 role formation？

如果作者不能直接回答这十个问题，审稿人应认为论文仍在概念阶段。

## 7. 对当前项目的审稿判断

以 2026-09-24 的项目状态，如果现在投稿，我会给 **Reject/Strong Major Revision**，原因是核心故事有意义，但三项 P0 仍未通过：

- 没有锁定唯一的 judgment→role update；
- 没有形成跨独立任务的未来职责变化；
- 没有得到能够与同信息 bandit、trust、Meta-Team/RAPS/C3 等区分的结果。

已有真实实验不是无用的：它们证明了传输、来源、评分边界、消费行为和成本记录中的具体困难，也排除了若干不干净的故事。但它们还不能支撑“角色形成方法有效”。

因此，当前最重要的审稿通过顺序是：

1. 完成 G0：写出一个单一、可反驳、带合法观察边界的更新规则；
2. 完成 G2/G3：让真实 producer–consumer 链能稳定产生可审计的判断、使用和返工事件；
3. 完成 G4：实现同信息强基线和明确停机条件；
4. 完成 G5：在独立 task/root 上测“判断 → 角色 → 未来职责”；
5. 完成 G6：根据质量、成本和负结果决定保留、收窄或关闭故事；
6. 只有通过后，才重写论文和主图表。

论文最终应当能够让审稿人相信三件事：

```text
这个判断来自真正受影响的协作者；
这个判断确实改变了未来职责；
这个改变带来的收益不是普通信任、任务难度或事后脚本造成的。
```

若实验只能证明第一件事，论文应写成“协作者判断是一个可用监督信号的边界研究”；若能证明前两件但不能超过强基线，应诚实报告“角色记录可运行但没有独立方法增益”；只有三件事同时成立，才有资格把故事写成 AAMAS 的方法论文。
