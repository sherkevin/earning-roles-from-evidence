## 1. Scope and method

This note analyzes the **20 failure cases** listed in each method's `failure_cases.md` for the paper's canonical `HotpotQA chain-200 / gpt-4.1-mini` run. The goal is modest but useful: identify **where** the current Stage-1 errors terminate in the delegation chain, which errors are **shared across all routing strategies**, and which errors are **method-specific**.

This is intentionally a **Stage-1 error-location taxonomy**, not a full semantic annotation study. It uses the reviewer-visible artifacts already committed in the repo:

- `artifacts/round2_gpt41mini/run_20260414_115739/fixed_peer_calibrated/failure_cases.md`
- `artifacts/round2_gpt41mini/run_20260414_115739/fixed_self_claim/failure_cases.md`
- `artifacts/round2_gpt41mini/run_20260414_115739/fixed_static_roles/failure_cases.md`
- companion `metrics.json` files in the same three directories

Why this is still useful:

1. It gives the paper a first **quantitative failure-mode table** rather than only isolated examples.
2. It distinguishes **routing-location effects** from **shared answer-generation bottlenecks**.
3. It provides a clean baseline for later expansion once multi-seed and external-baseline runs land.

## 3. Named failure modes

### FM-1. Long-chain synthesizer collapse

Definition: a question survives to the final `synthesizer` and is still answered incorrectly at `4-hop`.

Quantitative footprint:

- `fixed_peer_calibrated`: **20/20 failures = 100%**
- `fixed_self_claim`: **20/20 failures = 100%**
- `fixed_static_roles`: **10/20 failures = 50%**

Representative examples:

- `hotpotqa-0014` (`from 1986 to 2013` -> `1945 to 1969`)
- `hotpotqa-0044` (`Nelson Rockefeller` -> `Lyndon B. Johnson`)
- `hotpotqa-0082` (`Conscription` -> `requiring only men to register for the draft`)

Interpretation:

This is the clearest quantitative support for the paper's existing claim that, on the strong backbone, many residual Stage-1 errors are **not caused by failing to route far enough**. They survive the whole chain and fail at final aggregation / answer formation.

### FM-2. Shared answer-generation bottleneck across all three methods

Definition: the same sample is wrong under `peer_calibrated`, `self_claim`, and `static_roles`.

Quantitative footprint:

- shared across all three methods: **13 / 20 failures per method = 65%**
- among these shared failures, **9 / 13** terminate as `synthesizer@4` for **all three methods**

The 9 strongest "routing-invariant" shared bottleneck cases are:

- `hotpotqa-0014`
- `hotpotqa-0015`
- `hotpotqa-0018`
- `hotpotqa-0021`
- `hotpotqa-0035`
- `hotpotqa-0044`
- `hotpotqa-0074`
- `hotpotqa-0077`
- `hotpotqa-0082`

Interpretation:

These are the strongest candidates for a paper-level statement like:

> A large fraction of the remaining Stage-1 error mass is **routing-invariant** under the current prompt/backbone pair. In the canonical chain-200 run, 13 of the 20 errors made by each method are shared across all three routing strategies, and 9 of those 13 persist all the way to `synthesizer@4` in every method.

This is stronger and cleaner than the current vague prose "some remaining errors are generated by local answer bottlenecks rather than by routing failure."

### FM-3. Static pipeline short-chain evidence misresolution

Definition: the error terminates before the final `synthesizer`, typically at `evidence_seeker@2` or `verifier@3`.

Quantitative footprint for `fixed_static_roles`:

- `evidence_seeker@2`: **9 / 20**
- `verifier@3`: **1 / 20**
- short/mid-chain total: **10 / 20 = 50%**

`fixed_static_roles`-only failures:

- `hotpotqa-0023`
- `hotpotqa-0029`
- `hotpotqa-0034`
- `hotpotqa-0055`

These four cases are important because they are **not** shared with `peer_calibrated` or `self_claim`; they are the cleanest evidence that forcing a shorter fixed-role route creates a distinct failure family.

Representative examples:

- `hotpotqa-0023`: comparative question, wrong answer accepted at `evidence_seeker@2`
- `hotpotqa-0029`: entity retrieval / title resolution miss at `evidence_seeker@2`
- `hotpotqa-0034`: cardinality comparison miss at `evidence_seeker@2`
- `hotpotqa-0055`: location resolution miss at `evidence_seeker@2`

Interpretation:

This is the clearest evidence that `static_roles` is more vulnerable to **early evidence-selection or comparison-resolution mistakes**, while the other two methods tend to defer failure to final synthesis.

### FM-4. Small method-specific residue after the shared core

Method-unique failures:

- `fixed_peer_calibrated` only: **1** (`hotpotqa-0013`)
- `fixed_self_claim` only: **2** (`hotpotqa-0092`, `hotpotqa-0100`)
- `fixed_static_roles` only: **4** (`hotpotqa-0023`, `0029`, `0034`, `0055`)

Interpretation:

Once the shared 13-case bottleneck core is removed, the methods differ mostly in a **small residue set**:

- `peer_calibrated` still has one unique long-chain yes/no flip;
- `self_claim` has two unique over-specific / normalization-style long-chain misses;
- `static_roles` has the largest unique residue, dominated by short-chain evidence/comparison errors.

This again suggests that current Stage-1 differences are better described as **failure-location redistribution** than as a clean reduction in total error count.

## 4. Paper-ready takeaways

If we want to reuse this note in the paper later, the most defensible claims are:

1. **Shared bottleneck dominates**: 13/20 failures are common to all three Stage-1 methods.
2. **Long-chain synthesis is the main sink for peer/self methods**: 20/20 errors for `peer_calibrated` and 20/20 for `self_claim` terminate at `synthesizer@4`.
3. **Static roles fail earlier**: 10/20 `static_roles` errors terminate before final synthesis, including 4 method-unique cases.
4. **Current routing differences mostly move where failure happens, not how many failures remain**.

Compact prose candidate for later paper integration:

> A first quantitative error-location audit on the canonical chain-200 run shows that the residual Stage-1 error mass is dominated by a shared answer-generation bottleneck rather than by method-specific routing failures: 13 of the 20 errors made by each of the three methods are shared across all three, and for `peer_calibrated` and `self_claim` all 20 observed errors terminate at the final `synthesizer` (`4-hop`). By contrast, `static_roles` shows a distinct short-chain failure family, with 10/20 errors terminating earlier (`evidence_seeker@2` or `verifier@3`), including 4 cases unique to that pipeline. Under the current strong-backbone setting, routing choice therefore changes the *location* of residual failure more clearly than the *count* of residual failure.

## 5. Limitations of this note

1. This is still **single-run / single-seed / chain-200** analysis.
2. It uses the committed `failure_cases.md` artifacts, not a deeper semantic relabeling of all `routing_traces.jsonl`.
3. The taxonomy is **error-location-first**, not yet a full semantic taxonomy (e.g., entity aliasing, comparison inversion, temporal range, yes/no contradiction).

The natural next step is to extend this to a 2-axis matrix:

- **location axis**: `evidence_seeker@2`, `verifier@3`, `synthesizer@4`
- **semantic axis**: entity mismatch / comparison inversion / temporal range / answer normalization / yes-no contradiction

That extension would make a stronger appendix- or camera-ready-grade EXP-8 closure.
