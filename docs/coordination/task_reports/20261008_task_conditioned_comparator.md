# 任务条件对照与真实本地表示审计 — 2026-10-08

**推进点：补上了线性对照表达“任务不同、合适的人不同”的能力，并排除了会截断当前合同的直接编码方案。尚未得到真实任务收益或创新效果。**

## 目的、衡量与执行

上一轮主版维护属于已完成进展。本轮回到 ER-G2、方法标准 F.1/F.2 与 benchmark/baseline 的同信息对照要求。目的不是多跑模型，而是避免用只能估计候选均值的弱对照验证任务泛化。

开始前记录任务台账、原始需要及一手来源；两个Codex协作者分别检查数学/新颖性与本地复用/代码。执行前保存配置、源码摘要、模型revision及权重/配置/词表摘要；原始记录按阶段写入。没有外部实验API、新agent任务、GPU或新奖励标签。

验收指标为：分块更新与独立完整block ridge一致；人工交叉偏好可表达；未选状态、候选版本隔离；菜单排列/子集不改变同候选分数；真实本地encoder输入token覆盖和输出复现。人工标签只做软件/代数控制，不冒充真实交付标签。

## 结果与问题定位

| 检查 | 实际结果 | 意义与边界 |
|---|---|---|
| 身份/可加线性表示 | 数学上候选差值不随任务变 | 仅约束该头，不否定独立上下文base score或非线性reranker |
| 新增disjoint ridge对照 | 每轮22测试通过；四行人工控制得到两个相反排序 | 候选数值组件可用，不等于任务泛化有效 |
| 原菜单索引特征 | 菜单顺序决定坐标 | 历史固定菜单未证明污染；新实现按精确candidate@version取状态 |
| MiniLM实际CPU编码 | 2/4输入被截断，467 > 256 | 事后token边界检查确认丢失部分C4及C5/C6合同要求；不提升为完整输入 |
| BGE实际CPU编码 | 4/4输入完整，限长512；384维 | 只在这四份文本上确认token保留；不是最终backbone或语义效果 |
| 重复编码 | 两个模型各自最大绝对差约8.20e−8 | 只检查一次batch/单条CPU输出一致性，不是性能统计 |
| 向量接入数值头 | BGE有3/4原始向量范数略大于1；显式float64归一化至固定半径后4/4接受，0更新 | 保留原始向量、变换规则和输出；不伪称selection时已封存 |
| 历史输入恢复 | C1 selection binding只保存digest，不含完整captured_features | 有sidecar数据类型不等于已有可恢复的历史sidecar；不能回填 |

## 为什么保留画像融合

画像cosine匹配是双线性匹配的特例，能作为有意义的基线/候选；独立回归则提供任务条件的强对照基础。两者分别面临画像错误/负迁移与新Agent冷启动。384×384完整双线性模型若直接做全量ridge，Gram约162 GiB，不能套用小head的实时性结论。后续要用同信息消融决定是否采用压缩或残差，不能因这次离线算例锁定方法。

独立审查接受代数与窄范围输入覆盖修正，同时保留三条反对意见：task-only输入缺公开历史；generic role未覆盖完整接收方/状态；可计算和token完整不证明few-shot或效用。该意见已写进候选卡，没有投票代替科学证据。
