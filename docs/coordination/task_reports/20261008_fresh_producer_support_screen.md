## 为什么这改变下一步

此前固定的 native-bad/patched-good 对照可以验证代码、评分和事件接线，但不能
证明自然形成的 peer 能力差异。当前真实模型都修复了该序列化问题，因而不能把
旧静态对照继续当作训练选择器的自然信号。这个结论不撤销原来的创新主线；它
要求先找到对选人有实际后果的任务分布，才能检验主线。

下一步先审查已下载的第二 root 材料与原生协作信息需求，明确最简单的强控制
（例如直接转交合法任务说明）是否已经解决依赖；比较原生任务变化，而非继续
给固定时间戳检查购买判断。如果值得做新的共同 target 筛查，必须先解决完整
recipient 可见性、独立 terminal Y、J-before-A 与同信息控制，另立卡后再执行。
第二 root 的正式选择及方法的重要调整仍需共同确认，不在本卡里偷偷更换。

## 可复用实现与剩余限制

1. C1 新增可选 fresh producer 入口：候选版本绑定生成策略，本次 artifact 另有
   摘要；默认静态行为保留。新的 source→target route 可保存前后个人经历，
   但本轮没有执行该完整 route，不能把软件检查写成真实闭环证据。
2. 修复64 KiB回复许可与32 KiB个人历史上限冲突：回复最多8192个规范JSON字节，
   调用前按实际历史和预留回复检查容量，不静默截断。interaction_id 在调用前绑定。
3. 保留了 C1 的两个未解决限制：旧 J prompt 仅看 producer.py，旧 Y 是 recipient
   与 adoption 的合取。新工程 route 明示两点；本轮科学筛查不调用这条旧判断路线。

子协作者均使用 Codex gpt-6-sol。研究协作者与 benchmark 被测模型是不同角色；
实验延续既有获准的“内部”API配置，不是创建第三方研究 agent。审查者提到的
`usage:null` 汇总风险，原有生成器表达式实际上已有 usage_complete 过滤；本轮
额外采用 `or {}` 防御，但没有声称观察到了该崩溃。预算预留与真实请求开始分开记。
