# 项目收敛审查：完成了什么，缺什么，路线是否正确

初稿：2026-09-25；证据复核：2026-09-26。

性质：现有证据的收敛审查；不是新实验结果或 benchmark 冻结决议。科学门的定义和状态以 [AAMAS_TASKS](../coordination/AAMAS_TASKS.md) 为准。

## 当前结论

当前已经有两条真实限定协作链，后续assignment确实被消费，但反馈没有改变选择概率或选人，尚未证明判断有助于角色学习。四次N02尝试已耗尽；下一步先修正责任归因、交付评分覆盖与peer持久经验，再决定N03采样。benchmark、baseline、backbone和最终训练方法均没有收口。最新证据见[N02收口报告](n02_real_closed_loop_review_20260926.md)；下文程序夹具保留为历史工程证据。

最新 [causal_v2 原始记录](../../experiments/logs/peerrolebench_tb_vertical_20260926_causal_v2/raw.jsonl) 的 16 个程序夹具 episode 验证了选择顺序、消费产物和后续分配的使用。它有 0 次 LLM 调用，`scientific_claim_allowed=false`，尚未证明：

> 真实消费者判断 → 可归因的生产者角色证据 → 后续责任分配改变 → 留出任务上的团队质量与成本改善。

因此当前可以说“修复了会使实验测错问题的协议错误”，不能说“方法已经成立”“实时训练已经实现”或“benchmark 已经冻结”。

## 唯一应保留的主故事

主论文问题仍是 **learning roles from others' situated judgments**：

> 在初始能力和资源可比、信息受局部邻居和 selected-only 约束的协作流中，实际使用交付物的消费者给出的接受、返工或拒绝判断，能否形成可归因的生产者角色证据，改变后续任务的责任分派，并改善预先规定的团队质量–成本目标？

这里的 judgment 必须来自真实任务 owner 或 downstream consumer，且要记录实际使用/返工后果。与任务脱离的 LLM 评分、自我报告、纯终局奖励、静态接受率都不能替代这个对象。后续还必须区分“找到总体最强 peer”“消费者自己的私有信任”和“依据他人的情境化判断形成分工”。

单次委派诊断只检验必要信号，不能直接证明原始设想中的无中心调度、稀疏局部邻居与递归协作。高质量方法必须最终回到这一多智能体问题，而不能仅把通用在线分类器包装成角色学习。

## 方法与任务的关系

ArtifactRole / PeerRole 是当前科学任务的工作名称，承载真实交付、消费者判断、实际使用/返工、终局结果、角色更新和后续分配。TeamBench 只是优先审查的任务基底，尚未冻结为主 benchmark。

PeerSelect / Stream-JEV 是机制与共享工程层，研究局部候选、selected-only 延迟反馈、在线更新、探索和遗忘约束。graph-ipd 可作局部 peer selection 的机制检查，peer/tool 两项目可共享事件、选择概率、延迟队列、版本、快照与更新接口，但应保留各自目标和评价器。博弈 payoff、工具正确性不能代替真实消费者对交付物的判断。

RLS 是强比较基线；Laya 是候选表示模型；AnyJev 是可能复用的实现。它们都没有被确认为本项目最终 backbone 或论文创新。实时更新必须同时满足新情境质量、旧能力保留和反馈到生效的端到端时延要求，目前没有相应实证。

## 已完成的协议修复

[ADR 0015](../user/decisions/0015-select-before-execution-and-bind-later-assignment.md) 固定了执行前选择语义：先选择，只让被选中的 peer 执行；消费者生成实际消费产物；终局评分针对该产物；下一轮选择使用已记录的 assignment，并保留它的实际选择概率。负面证据可以使下一轮改选另一个 peer，不能要求 assignment 必须仍给被评价者。

strict ledger 已覆盖选择与交付绑定、判断与动作映射、终局结果到达后更新、每份交付的一次判断/动作/结果，以及禁止任务开始后补写选择或 assignment。2026-09-26 的追加核查又封住两个入口：同一 judgment/action 不能更换 ID 或版本重复更新；下一轮 selection 一旦记录，就不能再补写 assignment。协议测试由旧 9 项增至本轮复核的 15 项，测试通过只支持这些合约约束。

这些约束有助于检验原始故事，因为它们让过去反馈真正进入未来执行前的决策。它们本身是必要的测量与实现条件，不构成新学习机制。causal_v2 早于追加入口加固，执行时源码哈希保存在其 config；不能把当前测试通过说成历史运行使用了当前全部代码。逐项状态见[协议审计](peer_role_protocol_causality_audit_20260925.md)。

## 已有证据能说明什么

### 程序夹具：链路能够运行，条件之间没有收益差异

[causal_v2 摘要](../../experiments/logs/peerrolebench_tb_vertical_20260926_causal_v2/summary.json) 记录：两个 TeamBench 任务族、每族两个 seed、四个条件，共 16 个 episode，34.487 秒。逐行复核结果为：

- 16/16 只生成选中 peer 的交付；8/8 后续 episode 使用了 assignment。
- random 条件四次选择的 propensity 均为 1/3；此前 causal_v1 把第二次选择写成 1.0 的错误已在 v2 修正。
- 消费者动作共 `use=5`、`repair=9`、`independent_redo=2`；实际消费产物的源文件与评分副本一致，评分前后 source、tests、expected 的哈希未变。
- 平均终局分数为 0.8958，范围 0.5833–1.0；同一任务/seed 下四个条件的终局分数完全相同。

判断由 `fixture_judgment(peer_id)` 硬编码；所有 repair/redo 都调用同一套手写修复；`repair_cost` 只有 0/1，占位表示是否返工，没有实测 token、工具、人工或训练成本。CR2 两个 seed 的消费产物均得 1.0；DIST1 seed 0 得 1.0、seed 1 得 0.5833。高分不能归于选对了 peer，也没有展示角色学习或实时训练性能。

CR2 的首次资格检查保留了 12/13、3/13 的失败：包括尾逗号缺失，以及 grader 白名单硬编码 seed-0 文件名、未复制 seed-1 源文件。修复后两个 seed 均为 13/13。安装 `pytest-timeout==2.4.0` 后，DIST1 seed 0 的原始产物为 6/12、修复产物为 12/12；这不能推广为全部 seed 已合格。原始失败、secure_v4、causal_v1 均保留，详见[运行报告](peerrolebench_tb_vertical_slice_20260925.md)。

### 真实 API：已有判断/使用实例，仍没有纵向角色学习结果

真实协作记录并非空白。[AppWorld v5](../../artifacts/experiments/aamas2027/peer_judgment_resume_v5_20260923/report.md) 在同一个开发任务上新增 7 次真实响应，产生接受判断与三行匹配使用；官方结果是 5 项断言通过、1 项完成答案字段失败。它是单个判断/使用实例，且生产者来源引用仍不完整，没有执行 role update 或后续 assignment。

另一个 [TeamBench judgment 接口探针](../../experiments/logs/peerrolebench_real_judgment_20260925/raw.jsonl) 保留三次尝试：一次 TLS 失败、一次返回真实 JSON 后发生本地后处理错误、一次成功重跑。成功重跑记录 256 输入、700 输出 token；先前尝试的真实用量不完整。探针使用人工 diff 摘要和占位 artifact digest，支持真实传输与 JSON 解析可行，不支持真实产物绑定、接收者实际使用或完整进程隔离已经验证。

这两类证据应各自保留；不能把接口探针算作角色学习实验，也不能把已有的真实判断/使用实例抹去。

仅改consumer自身负责的文件。更新值等于先验0.5，未改变概率；同模型fresh peers
尚无持续个人经验。故纵向链路有了真实证据，纵向学习收益仍没有。

## 尚未解决的核心问题

| 缺口 | 为什么影响原始问题 | 下一次应取得的证据 |
|---|---|---|
| 主 benchmark / baseline 未冻结 | 当前 TeamBench 只是两个任务族、两个 seed 的候选；旧 ADR 0008 仍列 CooperBench / DecisionBench / AgentWorld | 任务来源、评分语义、真实上下游依赖、任务 root 层面的开发/留出划分与正式替代 ADR |
| 正式运行/评分资格未完成 | 固定runtime已通过列举访问/资源检查；native pytest仍同进程，非对抗consumer记录不可称防篡改 | 保留限定范围，补完整交付/消费义务覆盖；不要继续通用sandbox开发替代任务资格 |
| 真实反馈的信息价值未知 | 有判断或写入成功，不代表判断能预测未来任务中的 peer 适配 | 实测交付质量、消费者返工成本、最终质量，检查情境与他人评价的增量信息 |
| 缺少有持续信号的真实跨root闭环 | N02链路已通，但概率未变、peer无个人经验且只有一个root | 合法个人经验影响后续交付，情境化评价提供增量信号，并在独立任务root上检验 |
| 最终方法与训练创新未确定 | 简单模块组合可能被同信息 contextual trust/bandit 完整解释 | 一个有数学假设、复杂度、反例和淘汰条件的方法，与 RLS / online SGD / 周期重拟合公平比较 |
| 完整成本、遗忘和更新时效未测 | 0/1 返工标记不能支持质量–成本收益；单步矩阵计算不能支持实时性 | 总调用/token/工具成本、旧情境保留、变化后恢复、反馈到更新生效 p95 |

ADR 0015 只改变协议语义，没有取代 ADR 0008。不得同时把两套不同 benchmark 安排称为已冻结的 active 方案。

## 路线是否仍在推进目标

本轮有价值的进展是修复了“挑已有产物”“写了 assignment 却不用”“消费者返工后仍评分原交付”等会测错研究对象的问题。可复用资产是 TeamBench 的任务生成器与原生 scorer、现有协议账本、源文件复制与哈希审计、逐样本日志；这些已在本地 runner 中接上。

风险在于把更多程序运行、GPU 占用或 backbone 扫描当作科学进展。只有真实判断包含与任务/消费者有关的增量信息，并在未来分工中发挥作用，才有理由投入新训练机制。仅找到一个固定强 peer，或者被同信息 bandit 解释的收益，都不足以支持当前主故事。

接下来按主台账 N01–N05 推进：先完成一个任务基底的评分和隔离资格，再做最多 4 次真实接入尝试；接入合格后以包含这 4 次在内的最多 24 次开发尝试诊断信号，再冻结首次公平比较。A800 训练须由明确的数据/更新瓶颈、数学推导和有预算的实验卡驱动。每个小任务结束都检查是否增加了原始故事所需的证据，不能把诊断样本重解释为独立确认结果。
