# 原问题重启：真实任务边界与方法可辨识性

2026-09-23，G0/B5.3 的只读可行性审查。执行依据为[决议 0006](../../user/decisions/0006-study-peer-judged-role-formation.md)；正式要求和状态仍分别在 [REQUIREMENTS](../../paper/aamas2027/REQUIREMENTS.md) 与 [AAMAS_TASKS](../../coordination/AAMAS_TASKS.md)。本审查没有调用模型、运行新实验或锁定算法。

## 原问题的可测形式

在 agent 的私有经验和 workflow 都随合作变化时，某执行者交付的东西被**真正依赖它的接收者**如何使用、验收、返工，能否成为该执行者后续承担某类职责的可靠证据？预期因果链是交付 `z` → 接收者的实际使用/返工 `j` → 带来源与上下文的角色证据 `P` → 后续职责 `a` → 团队结果/总成本 `Y,C`。`P` 不是自报标签，也不同于某一个委派者私下的 `B_u(v)`。

各比较组需要同样的初始 agent/workflow 状态、任务机会、非目标状态更新规则、观察权限和预算；**运行中形成的能力与 workflow 不固定**。短程快照只诊断某条证据是否有信息，长期完整策略流才测试角色形成对分工和效用的作用。

这要求新增**真正的两个模型调用历史**与显式交付物。生产者只读；接收者拥有写入权并必须记录是否实际使用了交付，以及用多少额外工作修正。AppWorld 的单个 `execute` 环境含持久 Python shell，两个 prompt 若共用其变量就不是独立 agent；需要隔离各自记忆/私有变量，只经允许的交付物通信。双方只能访问任务指令、API 文档及公开运行观察；评分只在接收者行动与判断封存后离线进行。

现成 AppWorld episode 没有同伴评判、跨任务角色状态或未来分工。每个家族仅 3 个 sibling；train/dev generator 家族不重合。[B0 审查](../../../artifacts/analysis/aamas2027/appworld_b0_20260920/report.md)和已有单代理结果可复用为环境/成本基线，不能算本研究的多代理结果。开发集 `3ab5b8b_1/_2/_3` 有失败空间，但已被事后同源普通程序在 R3 全部解决，只能作为受污染的开发压力样本；任一新机制必须保留同信息程序/上下文信任对照。六家族 18 个 train 实例可扩大控制器与判断信号的开发诊断范围，但无法自动提供多评判者校准或长期角色学习的独立统计证据；重复重置同题也不是新样本。

## 方法上的关键判别

一个可执行的诊断候选是记录交付、实际使用、返工、评判者、职责和难度，并用抽查与后续可归因的结果修正评判错误，再更新执行者的语境化角色档案，用它影响后续分工。但这**尚不是创新点**：相同信息的上下文信任/bandit 可以重写成类似的估计器。[CADMAS-CTX](../../../references/aamas/peer_judgement_20260923/cadmas_ctx_v1.html)已有语境化同伴能力后验，[Meta-Team](../../../references/aamas/acquisition_followup_20260922/metateam_v1.html)已把下游同伴反馈用于队友画像和组织演化。接收者判断与后续分工若只是这些方法的换名，主张就不成立。

因此先检查三件事：真实独立接收者是否确实依赖生产者交付；其使用/返工在任务难度、评判者宽严和选择偏差之外是否有预测信息；让这类证据改变后续职责是否能在完整成本下超过同信息信任与 pooled 控制。旧 R0–R3 没有回答这些问题。下一个有意义的实验是预注册的小型**开发**诊断：固定上述角色隔离、允许观察、任务 ID、API 预算、验收时点和失败处理，保留每个模型调用与每例原始日志，再判断是否值得设计长期方法实验。这个审查本身不宣布 G0、B5.3 或论文科学门槛通过。

## 2026-09-23：v2 真实开发烟测的失败记录

[v2 报告](../../../artifacts/experiments/aamas2027/peer_judgment_smoke_v2_20260923/report.md)与[逐任务处理结果](../../../artifacts/experiments/aamas2027/peer_judgment_smoke_v2_20260923/processed_results.json)记录了预先固定的两个 `_2` train sibling；它们仍是研究侧看过 scorer 的开发题。共 7 次真实 API 尝试、5 次模型响应、2 次超时（这两次 token 用量未知）。`22cc237_2` 在任何世界调用前两次各约 120 秒超时；`3c13f5a_2` 虽得到 5 次响应、执行了 4 个世界步骤，但三次公开 `api_docs` 调用都因原生环境拦截 `pathlib.Path.mkdir` 失败，一次本地计算成功，第五次响应中的 `dir(apis)` 又被控制器的 `safe_code` 拒绝。没有成功的任务数据读取、有效交付物、接收者调用/判断/行动或官方评分。

此前 CPU 假 requester 的 guard fixture 不能证明原生 AppWorld 的公开文档路径可用；v2 的实际失败修正了这一点。处理报告核对了执行时 runner 快照、manifest、两份 episode header 的 SHA256；源配置与归档 `frozen_config.json` 的 JSON 值相同，但字节哈希不同，不能把源配置哈希说成归档副本哈希。当前瓶颈仍是合法观察链路与运行时的兼容性，不能据此判断同伴评判质量、角色形成或方法优劣；B5.3/G2 仍未完成。

## 2026-09-23：v4 交付封存、接收者判断未达成

[v4 报告](../../../artifacts/experiments/aamas2027/peer_judgment_smoke_v4_20260923/report.md)记录了在 v3 零响应、零世界操作后，以紧凑公开 prompt 对同一 `3c13f5a_3` 的一次开发续跑；它不是新增独立样本。7 次真实生产者响应执行了 6 个世界步骤，封存一份通过控制器 schema 与最小公开读取门槛的三行提案。三行都引用目录读取步骤 3，却没有引用真正读取账单与联系人信息的步骤 6，因此“控制器通过”不等于逐项来源已充分核验。接收者审阅阶段有 1 次真实模型响应，但代码从 `import apis` 开始，被 `safe_code` 在世界执行前拒绝；没有封存判断、接收者行动或官方评分。总计 8 次响应的 token、runner/config/proposal 哈希已与原始日志核对。该结果证明控制器走到了交付边界，也暴露来源粒度与接收者代码入口问题；对同伴判断信号、角色形成、方法效果或 prompt 长短的因果作用均无结论，B5.3/G2 仍未完成。

## 2026-09-23：v5 同一案例的真实接收者判断与官方失败

[v5 报告](../../../artifacts/experiments/aamas2027/peer_judgment_resume_v5_20260923/report.md)沿用 v4 原封存提案及那次在世界执行前被拒的接收者响应，在同一 `3c13f5a_3` 上新增 5 次真实审阅响应、2 次行动响应；两版连起来有 15 次响应，但 v5 **仅新增 7 次**，也没有新增独立样本。接收者用公开 API 自行核查账单、联系人和 Venmo 用户，行动前封存 `accept` 且 `intends_to_use_proposal=true`，然后成功创建与提案三行都匹配的付款请求。官方评分为 `success=false`：5 项通过，唯一失败是 `answers match`，因为接收者以冗长说明调用 `complete_task(answer=...)`，而标准答案为 null。私有评分只在行动封存后离线运行，未进入模型决策上下文。

这是一条真实的“交付→接收者判断→匹配行动”开发见证，但匹配使用不能证明行动由生产者提案造成：接收者做了独立核查；v4 提案仍遗漏真正读取账单与联系人信息的步骤 6 引用。v5 的两条 `supervisor.show_active_task` 审计事件因控制器在 `finally` 延迟写日志而出现在 `offline_evaluation` 行之后，源代码顺序表明调用发生在评分前，不能按原始行序误算为评分后的策略动作。单一受污染开发案例还不能估计判断信号质量或测试角色更新、后续职责与方法效果；B5.3 更广的门槛及 G2 仍未完成。
