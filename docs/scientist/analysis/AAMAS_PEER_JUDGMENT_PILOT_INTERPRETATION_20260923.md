# 原问题的一条真实交付链：局部验收、实际使用与终局失败

2026-09-23，**开发集单例诊断，不是方法实验或论文主结果**。受[决议 0005](../../user/decisions/0005-retain-peer-judged-role-learning.md)与[0006](../../user/decisions/0006-study-peer-judged-role-formation.md)约束，本文只解释一条真实 API 轨迹对“他人判断如何形成角色证据”意味着什么。v4 与 v5 是同一 `3c13f5a_3` 任务的连续实验，不是两个独立样本。v5 沿用 v4 已封存的生产者交付；v4 接收者的第一条回复在执行前被代码校验拒绝，未改变其世界。

## 对方法的约束，而非已经确定的方法

这条轨迹把至少四种状态分开了：`生产者交付的动作内容`、`交付的来源可审计性`、`实际接收者的验收与使用/返工`、`终局中可归于哪位执行者的错误`。如果只记录验收，来源引用缺陷会消失；如果只按终局失败给整条链扣分，三笔有效交付也会被误罚。最小的**待检候选**是给生产者记录“在此类依赖下被真实接收者使用、无需返工”的带上下文证据，同时记录来源支持与复核成本的不确定性；后续终局证据只修正可归因的部分，不把接收者的完成回报失误倒灌给生产者。上述候选可以被同信息的情境信任/上下文 bandit 模拟，**目前不是已成立的创新点**。

下一步必须用预先选定的多条独立任务、持续身份和后来职责选择检验三件事：接收者验收/实际使用在控制任务难度、评判者宽严与选择偏差后有没有预测信息；来源检查与终局纠错能否提高这个信号的可靠性；这份角色证据是否在完整复核成本下改变后续局部分工并优于同信息简单规则和近邻方法。一条轨迹不能估计这些量，也不能证明角色已经学会或投稿论点成立。AppWorld 的 [18 项 train 候选](AAMAS_PEER_JUDGMENT_FEASIBILITY_20260923.md)只能作开发可行性测试；确认集必须另行冻结并隔离本地可见的标签文件。
