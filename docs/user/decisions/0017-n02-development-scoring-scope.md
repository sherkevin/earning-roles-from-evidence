# 0017：N02 开发接入的评分范围

状态：已采纳为已授权路线的执行范围说明；不是最终 benchmark 或方法冻结。
日期：2026-09-26。

## 背景

N01 发现 TeamBench DIST1 原生 grader 没有运行实际 consumer，不能回答交付物
是否被接收者正确使用。原生 pytest 又与候选代码共享地址空间，无法靠外层 sandbox
保证 Python 调用帧中的断言隐藏。仅为四条接入重写全部原生测试会扩大研究无关工程。
独立审查建议保留严格资格未过的结论，同时允许一个范围更小、可审计的开发接入。

## 决定

1. N02-dev-v1 只执行预先固定的两个实例 seed 0/1，均来自同一 DIST1
   结构 root；失败不补跑。占用 N02 的最多四次与开发总共二十四次预算。
2. 本轮不执行原生 grader。评分仅为新增且版本化的实际 consumer 行为检查，
   四个检查不能称为完整任务正确率、原生 TeamBench 分数或独立生产者质量。
3. 候选代码只在已检查的 sandbox-runtime 中执行。源文件只读，网络与创建子进程
   被禁止；父评分断言、期望值、账本与其他样本不向候选进程开放。
4. 采用非对抗式代码开发诊断假设。公开 driver 和候选代码共享内存，记录并非
   防篡改。执行前检查候选源码，不允许主动探测评分器；不宣称抵御恶意 Python。
5. 接收者修复后的成功不作为原生产者交付正确的标签。源码审查判断、选择动作、
   消费者执行成本与消费后行为分分别记录。未知评分不生成 false 终局或更新。
6. 首轮选择是独立固定随机种子下的 uniform 抽样，接受实际抽样结果；第二轮
   消费者是首轮未参与者，其控制器合法接收首轮评价者的证据并作下一次选择。
7. 使用简单可解释的概率更新只为验证接线，不认作最终算法或创新。没有训练模型，
   不固定 Laya/AnyJev 等 backbone，不增加 GPU 作业。

## 理由

这两条诊断能够发现真实模型输出、交付读取、动作权限、消费执行和后续分配之间
的断点，比继续夹具测试更接近研究对象。缩小实际执行的评分面，还避免把原生
同进程 hidden-test 隔离未解决的问题带入本轮标签。

## 后果与边界

原 N01 严格门和 N02 完整验收继续开放：独立交付质量、原生评分资格与更多结构
尚未补齐。两个同结构实例不支持跨任务泛化、角色形成、局部网络收益或效果对比。
任何泄漏即停；首轮没有有效判断/消费/终局时，本版停止，不编造一条更新链。
